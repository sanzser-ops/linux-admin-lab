# Troubleshooting 01 — Alertmanager Gmail SMTP Authentication

> **Area:** Monitoring / Alertmanager / Gmail SMTP  
> **Severity:** Notification failure  
> **Status:** Resolved

---

## 1. Problem

Alertmanager was correctly receiving the `High CPU Usage` alert generated by Grafana, but the email notification was not being delivered.

The alert itself was working correctly, so the investigation focused on the notification and SMTP delivery path.

---

## 2. Symptoms

The alert was visible through the Alertmanager API:

    curl -s http://localhost:9093/api/v2/alerts

The response showed:

    alertname: High CPU Usage
    server: rhel-server-01
    receiver: email
    state: active

This confirmed that the alert had reached Alertmanager.

However, no email was initially received.

---

## 3. Investigation

### 3.1 Check Alertmanager logs

The first step was to inspect the Alertmanager service logs:

    sudo journalctl -u alertmanager --since "10 minutes ago" --no-pager

The important error was:

    535 5.7.8 Username and Password not accepted

The complete error indicated that Gmail was rejecting the SMTP authentication attempt:

    email.loginAuth auth: 535 5.7.8 Username and Password not accepted

### What this tells us

Alertmanager was able to communicate with the Gmail SMTP server.

The failure occurred during authentication.

Therefore, the problem was not:

- Alert generation
- Alertmanager connectivity
- SMTP hostname
- SMTP port
- Alertmanager routing

The evidence pointed specifically to the SMTP credentials.

---

### 3.2 Verify the SMTP configuration

The SMTP configuration was checked with:

    sudo grep -E 'smtp_(from|auth_username|smarthost)' /etc/alertmanager/alertmanager.yml

The configuration contained:

    smtp_smarthost: 'smtp.gmail.com:587'
    smtp_from: 'aptgetcorreo@gmail.com'
    smtp_auth_username: 'aptgetcorreo@gmail.com'

The configuration also required TLS for the SMTP connection.

The expected notification path was:

    Alertmanager
         |
         | SMTP
         v
    smtp.gmail.com:587
         |
         | TLS + authentication
         v
       Gmail
         |
         v
    Recipient mailbox

---

### 3.3 Verify the Alertmanager configuration

After changing the credentials, the configuration was successfully loaded by Alertmanager.

The service logs showed:

    Loading configuration file
    Completed loading of configuration file
    Listening on address=[::]:9093

This confirmed that the configuration was syntactically valid and Alertmanager was able to start normally.

The service was also confirmed to be running:

    sudo systemctl status alertmanager --no-pager

Expected result:

    Active: active (running)

---

### 3.4 Check the stored SMTP credential

The SMTP password was managed through Ansible Vault rather than being stored directly in the playbook.

The encrypted secret was stored in:

    ansible/group_vars/all/vault.yml

The relevant variable was:

    vault_smtp_password: "..."

The actual password is intentionally not documented in this repository.

The password is injected into the Alertmanager configuration by Ansible:

    smtp_auth_password: '{{ vault_smtp_password }}'

This allows the playbook to reference the secret without storing the actual credential in the Git repository.

---

### 3.5 Verify that the Vault file is protected

The Vault file was excluded from Git through `.gitignore`:

    ansible/group_vars/all/vault.yml

This was verified with:

    git check-ignore -v ansible/group_vars/all/vault.yml

Git confirmed that the file was ignored.

The following command was also used:

    git ls-files ansible/group_vars/all/vault.yml

No output confirmed that the secret file was not part of the Git repository.

---

## 4. Root Cause

The root cause was an invalid Gmail SMTP authentication credential.

The key evidence was:

    535 5.7.8 Username and Password not accepted

The complete monitoring pipeline was working until the final SMTP authentication step.

    Prometheus
        |
        v
    Grafana Alert Rule
        |
        | High CPU Usage
        v
    Alertmanager
        |
        | SMTP authentication
        X
      Gmail

The failure occurred here:

    Alertmanager ---> Gmail SMTP
                         ^
                         |
                    Authentication
                        FAILED

### Components confirmed to be working

| Component | Status |
|-----------|--------|
| Prometheus metrics | Working |
| Prometheus query | Working |
| Grafana alert rule | Working |
| Alert generation | Working |
| Alertmanager | Working |
| Alertmanager API | Working |
| Alertmanager routing | Working |
| Gmail SMTP connection | Reachable |
| Gmail SMTP authentication | Failed |
| Email delivery | Failed |

Therefore, the problem was specifically related to Gmail SMTP authentication.

---

## 5. Resolution

The Gmail SMTP credential was replaced with the correct Gmail application password.

The credential was stored securely using Ansible Vault.

The Alertmanager deployment was then executed with:

    ansible-playbook playbooks/alertmanager.yml -K --ask-vault-pass

The playbook completed successfully:

    PLAY RECAP

    rhel-server-01 : ok=14 changed=0 unreachable=0 failed=0 skipped=0 rescued=0 ignored=0

Alertmanager was restarted as part of the deployment.

---

## 6. Validation

### 6.1 Verify Alertmanager service

The service was checked with:

    sudo systemctl status alertmanager --no-pager

Result:

    Active: active (running)

This confirmed that Alertmanager started successfully after the configuration change.

---

### 6.2 Verify Alertmanager logs

The service logs were checked again:

    sudo journalctl -u alertmanager --since "2 minutes ago" --no-pager

The logs showed:

    Loading configuration file
    Completed loading of configuration file
    Listening on address=[::]:9093

No configuration error was reported.

---

### 6.3 Verify the alert

The alert was triggered again and checked through the Alertmanager API:

    curl -s http://localhost:9093/api/v2/alerts

The alert appeared with:

    alertname: High CPU Usage
    server: rhel-server-01
    receiver: email
    state: active

This confirmed that Alertmanager was receiving the alert correctly.

---

### 6.4 Verify email delivery

After correcting the SMTP credentials, the alert email was successfully received.

The notification path was now working:

    High CPU Usage
          |
          v
       Grafana
          |
          v
    Alertmanager
          |
          v
      Gmail SMTP
          |
          v
      Email received

---

### 6.5 Verify resolved notification

When CPU usage returned below the configured threshold, the alert changed to the resolved state.

The resolved notification was also successfully received.

This confirmed both notification paths:

    ALERT FIRING
         |
         v
    Email received

and:

    ALERT RESOLVED
         |
         v
    Resolved email received

This was important because the Alertmanager configuration contained:

    send_resolved: true

Therefore, both the firing and resolved notification paths were validated.

## 9. Security Considerations

The SMTP credential is a sensitive secret and must not be committed to Git.

The repository therefore uses Ansible Vault:

    ansible/group_vars/all/vault.yml

The file is excluded through:

    .gitignore

with:

    ansible/group_vars/all/vault.yml

The playbook only references the Vault variable:

    smtp_auth_password: '{{ vault_smtp_password }}'

The repository therefore contains the automation logic without exposing the actual credential.

---

## 10. Lessons Learned

- When an alert is not generating an email, first determine whether the alert reached Alertmanager.
- The Alertmanager API can be used to separate alert-generation problems from notification-delivery problems.
- Alertmanager logs provide the most useful information when troubleshooting notification failures.
- A `535 5.7.8` SMTP error indicates an authentication problem with the SMTP server.
- Gmail SMTP credentials should be handled securely.
- Sensitive credentials should never be committed to Git.
- Ansible Vault can be used to keep sensitive credentials outside normal repository files.
- `.gitignore` helps prevent accidental commits of local secret files.
- A configuration can be syntactically valid while still containing invalid credentials.
- A successful Alertmanager restart does not prove that email delivery works.
- Monitoring validation should test both the firing and resolved states of an alert.
- A successful alert does not necessarily mean the complete notification pipeline is working.
